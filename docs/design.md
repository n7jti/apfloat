# apfloat design

This document describes the current implementation and its intended contract. Source and tests are authoritative if they differ; update this document when either changes. It is intended for maintainers, users, and future AI-assisted work, not as a roadmap or an assurance of full IEEE 754 compliance.

## Requirements and scope

- Implement arbitrary-precision **binary** floating-point arithmetic in C++17, with a portable CMake build and a static library usable on Windows/MSVC and 64-bit Raspberry Pi OS/Linux.
- Give each value mutable precision, defaulting to 128 significand bits. Support decimal input and output, comparison, and addition, subtraction, multiplication, division and square root.
- Default to round-to-nearest, ties-to-even and provide explicit directed rounding for arithmetic, parsing, and precision changes. Support signed zero, infinity and NaN with IEEE-style behavior, without claiming complete IEEE 754 conformance.
- Return explicit errors for expected invalid input and precision. Permit operands of differing precision and use the greater precision for arithmetic results.
- Include dependency-free unit, functional and informational performance tests and Windows and native Pi CI. Pi runs are manually dispatched on the default branch and use a manually started self-hosted runner.

## Components and public API

[The public header](../include/apfloat/apfloat.hpp) exposes `apfloat::number`, `apfloat::error`, and the legacy `apfloat::precision_mismatch` exception type. The implementation is in [apfloat.cpp](../src/apfloat.cpp). `number` defaults to positive zero at 128 bits; `precision()` inspects precision, `set_precision()` changes it, `parse()` writes to an existing destination using that destination's precision, and `to_string()` returns exact decimal text. Named functions implement arithmetic and operators implement comparisons; binary results use the greater operand precision.

There are no public integer, native floating-point, or string constructors; parsing is the entry point for numeric text. Arithmetic functions require an explicit rounding mode; parsing and precision changes default to nearest-even but also accept a mode. There is no public status flag, NaN payload, or API for direct inspection of the sign or classification. Consumers may compare or format values, subject to the precision rules.

## Value model and limits

Each instance stores precision, a kind (`finite`, `infinity`, or `nan`), a sign, a 64-bit binary exponent, and an unsigned significand in a vector of 32-bit limbs, least-significant limb first. A finite value represents `(-1)^sign * significand * 2^exponent`. An empty significand represents signed zero. Nonzero finite significands produced by the rounding routine have exactly the selected number of significant bits, including trailing zero bits. Static assertions require 32-bit `unsigned int` and at least 64-bit `size_t`; intermediate limb arithmetic uses 64-bit unsigned integers.

Precision ranges from 1 through `number::maximum_precision` bits (`INT64_MAX / 64`), leaving headroom for intermediate bit counts and exponent calculations; practical capacity also depends on available memory. The highest set bit of a nonzero finite result has a binary exponent in [-2^40, 2^40]. There are no subnormal values: below the minimum, nearest rounding selects signed zero or the minimum normal magnitude, including the tie to zero; directed rounding selects the applicable bounding value. Nearest overflow yields signed infinity; directed overflow selects infinity or the maximum finite magnitude according to its direction. Large-scale operation and conversion performance remains unverified.

Changing precision immediately rounds a finite value to the new precision in the selected direction. Increasing precision preserves the represented value but does not restore lost bits. Special values retain their kind and sign. Invalid precision is reported and leaves the destination unchanged.

## Algorithms and rationale

The private integer helper implements comparison, shifts, addition, subtraction, multiplication, small-integer operations, and division. Multiplication uses schoolbook arithmetic for small operands, Karatsuba for intermediate sizes, and exact number-theoretic transforms with two moduli for large balanced operands. Larger unbalanced products are split into balanced blocks. Both moduli support transforms through 2^23 points. Inputs use base-2^16 digits; since each input has at most 2^22 digits at that transform size, each convolution coefficient is below 2^22 * (2^16 - 1)^2 < 2^54, well below the product of the moduli (> 2^58), so CRT reconstruction is unique. The transform falls back to Karatsuba for larger inputs.

Division uses fast paths for powers of two, single-limb divisors and common powers of two. Normalized limb-based long division handles small divisors and short quotients; larger divisions use recursive 2n-by-n and 3n-by-2n blocks. Each 3n-by-2n step estimates the quotient from the upper half of the divisor, multiplies it by the lower half, and corrects any overestimate using exact integer arithmetic. The normalized divisor bounds the estimate, and the resulting quotient and remainder satisfy `a = q*b + r` and `0 <= r < b`. Square root makes the input exponent even, scales the significand to the selected precision, then computes its integer floor root with a recursive high-half estimate and exact quotient correction. The integer remainder selects the requested bound; nearest rounding compares it with the midpoint, which cannot be exact for an integral scaled radicand. Decimal conversion reuses these integer operations. Standard-width intermediates avoid runtime dependencies and compiler-specific 128-bit types. The opt-in scale suite now exercises general division, directed `sqrt(2)` bounds, and decimal formatting/parsing at 33,219,413-bit precision; target-hardware results are required before treating those workloads as validated.

The shared `rounded` routine receives an unsigned numerator, denominator, binary scale, precision, sign and rounding mode. It determines the leading exponent, handles range boundaries, scales to the requested precision, divides to obtain a quotient and remainder, and rounds according to the requested mode. Nearest-even uses twice the remainder and the quotient's low bit; directed rounding increments only when the value is inexact and the requested direction is away from zero. A carry may increment the exponent. Addition and subtraction align significands before combining them; when their leading exponents differ by at least the result precision plus two, the smaller value is strictly less than a quarter of the larger value's result-precision ulp. A signed quarter-ulp surrogate preserves nearest and directed rounding without allocating for the exponent gap. Multiplication forms an exact integer product; division forms an exact rational; each uses the same rounding path. Comparisons align significands logically, without allocating a shifted copy, and compare the stored values exactly across precisions.

The parser removes leading and trailing significand zeroes, then groups decimal digits and uses divide-and-conquer conversion into an integer rational, converts it through the same rounding path, and accepts lowercase `inf`, `infinity`, and `nan`, each optionally signed. It rejects whitespace and malformed text. The input significand digit count and absolute effective decimal scale are limited to `number::maximum_precision / 8`, and the explicit exponent magnitude to twice that bound, leaving headroom in 64-bit intermediate size calculations. Formatting converts the exact binary value using shifts or powers of five and divide-and-conquer decimal conversion, and emits exact decimal text, not necessarily the shortest text. A NaN formats as `nan`; its input sign is not retained in text.

Special arithmetic handles infinities, zero and NaN before finite arithmetic. Positive and negative zero compare equal. NaN compares unequal to every value, including itself, and ordered comparisons involving NaN are false. A zero divided by zero, infinity divided by infinity, zero multiplied by infinity, and opposite infinities added produce NaN; finite nonzero division by signed zero produces signed infinity. Square root preserves signed zero, yields NaN for negative finite values and negative infinity, preserves positive infinity and NaN, and rounds positive finite roots at the operand precision. See [unit tests](../tests/unit.cpp) for representative cases.

## Error handling and failures

`parse` reports `invalid_syntax` or `out_of_range`; `set_precision` reports `invalid_precision`. Both return `none` on success and leave the destination unchanged on reported errors. Overflow and underflow in numerical operations are represented by infinity or zero/minimum finite as described above, not by error codes. Ordinary IEEE-style invalid operations yield NaN.

Binary arithmetic accepts differing operand precisions; even special results have the greater operand precision. The legacy `precision_mismatch` type is retained for compatibility but is not thrown by mixed-precision operations. Allocation and other unexpected exceptions propagate. OS faults such as access violations are not portable C++ exceptions and are not handled by the library.

## Build, tests, and CI

[CMakeLists.txt](../CMakeLists.txt) builds the `apfloat` static library, publishes the `apfloat::apfloat` target, installs headers and CMake package files, and enables CTest through `BUILD_TESTING`. [The consumer example](../tests/consumer/) validates the installed package.

[Unit tests](../tests/unit.cpp) cover rounding, edge cases, special values and errors, including exhaustive small and randomized recursive square-root cases with independently derived integer bounds. [Functional tests](../tests/functional.cpp) check multi-limb fixtures, small integer arithmetic, native-double division comparisons and decimal round trips. On Linux, [Pi script tests](../tests/pi-scripts.sh) exercise setup and session behavior with isolated mocked commands. The [benchmark](../tests/benchmark.cpp) records parse, format and arithmetic samples at 64, 128 and 256 bits, including comparison overhead used to consume each result. It emits CSV; results are informational, not performance regression gates.

The [Windows workflow](../.github/workflows/windows.yml) runs on pushes, pull requests and manual dispatch. The [Pi workflow](../.github/workflows/raspberry-pi.yml) is manually dispatched, runs its job only on the default branch, requires a Linux ARM64 runner with the `raspberry-pi` label, and uploads package and benchmark artifacts. [Pi scripts](../scripts/) provision a dedicated `gitrunr` account, separate administrator package installation from runner registration, and start the runner in the foreground. The account has a locked password and no sudo privileges; the administrator switches to it interactively. Runner-local state is outside the project. A workflow file or mock test does not establish that a real Pi run has passed; check the actual Actions run for hardware validation.

## Security, limitations, and maintenance

The Pi runner executes code on its host and GitHub warns against self-hosted runners for public repositories. Manual dispatch and default-branch restrictions reduce exposure but do not protect against a malicious authorized workflow change or other matching queued jobs. Restrict access, never run untrusted code, and keep the runner offline when not needed. Credentials and Pi login information must not be stored in this repository; machine-local runner authentication state uses normal protected filesystem permissions.

The design favors portable exact-integer calculations. Large decimal inputs, large precision and long formatted output may require substantial time and memory. Full IEEE 754 interchange formats, subnormals, status flags, and NaN payloads are not implemented. Tests provide finite coverage and do not prove all rounding and range cases correct. Keep this document, README and tests synchronized with any future behavior changes.
